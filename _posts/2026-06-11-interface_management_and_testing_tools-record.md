# 从零扩展一个综合接口调试工具后端的实践记录

最近我基于一个已有的 Spring Boot 后端项目，逐步将它扩展成了一套“综合接口调试工具”的后端服务。整个开发过程并不是简单堆接口，而是在尽量不改变原技术栈、不随意增加依赖的前提下，持续梳理业务关系、补齐数据模型、统一接口风格，并通过脚本做自动化冒烟测试。

本文记录这次后端扩展的设计思路、关键实现和踩坑点。文中已对真实路径、数据库地址、账号密码、Token、内网信息等敏感内容做脱敏处理。

## 技术栈与开发原则

项目原本使用 Java + Spring Boot 作为后端框架，数据访问层使用 MyBatis-Plus，数据库使用 MySQL，同时已有 Spring Security 与 JWT 登录鉴权能力。

我在开发过程中保持了三个原则：

1. 不随意更换技术栈，不为了单个功能引入额外依赖。
2. 继续沿用项目已有的统一响应结构 `ResponseDTO`。
3. 保持接口字段风格一致，新增业务接口统一使用下划线字段，例如 `project_id`、`model_id`、`data_format`。

这种策略的好处是开发节奏稳定，新增模块能够自然融入原项目，而不是形成一批风格割裂的新代码。

## 第一阶段：测试用例与测试结果管理

最开始实现的是测试用例管理和测试结果管理。

测试用例包含项目、模型、创建人、创建时间等信息。后来根据业务设计调整，测试用例不再需要审核状态，只保留新增、查询、详情、删除。

测试结果的规则更特殊：它不允许单独新增，而是在创建测试用例时自动生成。删除测试用例时，对应测试结果会同步删除；但删除测试结果时，不会反向删除测试用例。

这个设计让测试结果始终来源明确，避免出现没有测试用例支撑的孤立结果数据。

## 第二阶段：用户、项目、模型与权限

用户管理基于系统原有用户表和角色表扩展，支持新增、查询、删除和重置密码。其中新增、删除、重置密码只允许管理员和超级管理员操作，普通用户只能查询。

项目管理中，权限规则进一步细化：只有项目管理员才能编辑和删除项目。项目管理员由 `manager_id` 指向具体用户。

模型与项目之间没有做强制循环依赖。模型可以先创建，不绑定项目；后续创建项目时传入 `model_ids`，系统会自动把模型的 `project_id` 回填为当前项目。这种方式更符合实际使用流程，也避免了“创建项目必须先有模型，创建模型又必须先有项目”的循环问题。

## 第三阶段：数据格式管理的重构

数据格式管理是这次开发中比较关键的一次调整。

最初实现中，数据格式接口查询时会读取项目根目录下的某个 JSON 文件，并把文件内容作为接口响应返回。这个方式可以快速跑通，但有明显问题：如果文件被删除或移动，接口返回就会失效。

后来我将其改造成“文件只作为导入来源，数据库保存最终内容”的模式：

1. 用户可以通过 JSON 请求体提交数据格式内容。
2. 用户也可以上传 JSON 文件。
3. 后端解析并校验 JSON。
4. JSON 内容保存到数据库字段中。
5. 后续查询直接从数据库读取，不再依赖原文件。

数据库字段也从短字符串调整为适合保存完整 JSON 内容的文本类型。这样即使原始 JSON 文件被删除，已经入库的数据格式仍然可用。

## 第四阶段：引入字典表

随着字段类型、结构类型、项目状态等选项逐渐增多，我引入了通用字典表。

字典分为两张表：

- `dict_type`：维护字典类型，例如字段数据类型、字段结构类型。
- `dict_item`：维护具体选项，例如 `BYTE`、`LONG`、`enum`。

字典模块支持增删查改，并提供按 `type_code` 查询启用字典项的接口。写操作仅允许管理员和超级管理员，查询接口则对登录用户开放。

这里有一个设计取舍：我没有把项目、模型、测试用例这类核心业务实体放入字典。字典只适合维护低频变化的枚举型、选项型数据，不能替代业务表。

## 第五阶段：接口自动化冒烟测试

为了验证模块之间的联动关系，我编写了一个 PowerShell 冒烟测试脚本。脚本会自动生成唯一测试数据，按顺序调用接口，并在测试结束后清理数据。

脚本覆盖内容包括：

- 登录并获取 Token。
- 用户新增、查询、重置密码、删除。
- 普通用户访问管理员接口的权限校验。
- 字典类型和字典项的增删查改。
- 数据格式 JSON 入库和文件上传导入。
- 模型创建、项目绑定、模型 `project_id` 自动回填。
- 项目管理员编辑和删除项目。
- 创建测试用例后自动生成测试结果。
- 测试结果不允许单独新增。
- 删除测试结果不影响测试用例。
- 删除测试用例后同步删除结果。

一次完整运行后，脚本输出类似：

```text
Summary: passed=52 failed=0
```

这类脚本对后端业务开发非常有帮助。它不替代单元测试，但能快速确认主流程是否被破坏。

## 第六阶段：代码自检与低风险重构

功能完成后，我做了一轮代码自检，重点寻找重复但可安全合并的部分。

最终抽取了两个工具能力：

1. Controller 统一响应构造工具  
   将多个 Controller 中重复的 `buildResponse` 逻辑集中维护，统一处理成功、404、403、400 等状态码。

2. 当前用户与管理员权限校验工具  
   将 JWT 解析当前用户 ID、管理员角色判断等逻辑抽离出来，避免散落在多个业务服务中。

我没有强行抽取所有分页校验和 ID 校验。虽然这些代码有重复，但每个模块的错误提示和字段约束略有差异，过度抽象反而会降低可读性。

## 收获与总结

这次开发最大的体会是：后端接口开发不只是“把接口写出来”，更重要的是持续梳理业务关系。

项目、模型、数据格式、测试用例、测试结果之间存在明显的关联链路。如果一开始没有处理好绑定关系，后面接口调试会不断出现看似随机的问题。

比较有效的做法是：

- 先保证数据模型关系清楚。
- 再实现基础增删查改。
- 然后补权限控制。
- 最后用自动化脚本串联主业务流程。

在不更换技术栈、不引入额外依赖的情况下，这个项目已经从基础后端逐步扩展成了一个结构较清晰、接口较完整、可自动验证主流程的综合接口调试工具后端。
